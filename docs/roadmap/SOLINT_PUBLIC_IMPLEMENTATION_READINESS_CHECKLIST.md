> این چک‌لیست برنامهٔ کار است، نه مدرک انجام‌شدن کار یا تأیید امنیتی. مواردی که هنوز بررسی یا اجرا نشده‌اند باید باز بمانند. به‌خصوص قابلیت‌های سلامت، احراز هویت، ذخیرهٔ آفلاین و همگام‌سازی نباید صرفاً بر اساس نمایش موفق رابط کاربری آمادهٔ انتشار تلقی شوند.

## 1. قواعد استفاده

برای هر مورد یک مسئول، وضعیت، مدرک قابل بازبینی و تاریخ تعیین کنید. وضعیت‌های پیشنهادی:

- `NOT STARTED` — شروع نشده
- `IN PROGRESS` — در حال انجام
- `BLOCKED` — مسدود، همراه با دلیل و وابستگی
- `IN REVIEW` — آمادهٔ بازبینی
- `DONE` — فقط پس از پذیرش و ثبت مدرک
- `NOT APPLICABLE` — همراه با توجیه و تأیید

هر مورد بحرانیِ باز، شروع پیاده‌سازی بخش وابسته را متوقف می‌کند. عبور از یک دروازه باید با تأیید مالک محصول، مهندسی، امنیت/حریم خصوصی و در صورت ارتباط، مسئول بالینی ثبت شود.

## 2. پیش از شروع: تعیین محدوده نسخه اول

- [ ] مشخص‌کردن کاربران هدف و مسئله‌ای که نسخهٔ اول حل می‌کند.
- [ ] انتخاب قابلیت‌های داخل MVP و ثبت قابلیت‌های خارج از MVP.
- [ ] تفکیک قابلیت‌های نمایشی/نمونه از قابلیت‌های متصل به سرویس واقعی.
- [ ] تعیین اینکه در MVP اطلاعات واقعی سلامت دریافت یا ذخیره می‌شود یا خیر.
- [ ] تعیین بازار و حوزهٔ قضایی عرضه و آغاز بررسی حقوقی/حریم خصوصی متناسب با آن.
- [ ] تعیین مسئول تأیید محتوای سلامت و قواعد هشدار/ارجاع، اگر محتوای بالینی در MVP وجود دارد.
- [ ] تعریف معیارهای موفقیت محصول، بدون تبدیل معیارهای تجاری به ادعای ایمنی یا اثربخشی بالینی.
- [ ] ثبت تصمیم‌های باز و فرضیات در قالب ADR یا فهرست تصمیم‌ها.

**خروجی لازم:** سند محدودهٔ MVP، فهرست خارج از محدوده، فرضیات و تصمیم‌های باز با مالک و موعد.

## 3. دروازه صفر — بازبینی Phase 0 و آمادگی معماری

- [ ] مرور سند معماری مادر، سند هویت/آفلاین و سند Phase 0؛ رفع تعارض‌های میان آن‌ها.
- [ ] تهیهٔ نمودار context، اجزای اصلی، مرز اعتماد و جریان داده.
- [ ] تعیین مالکیت داده بین PUBLIC و NETWORK؛ تا زمان مشاهدهٔ واقعی مستندات NETWORK، هیچ ساختار یا قابلیت آن فرض‌شده تلقی نشود.
- [ ] تعیین قرارداد و نسخه‌بندی API؛ تأیید اینکه ارتباط PUBLIC و NETWORK صرفاً از API مجاز است.
- [ ] تعیین مرز ماژول‌ها و وابستگی‌های مجاز در Modular Monolith.
- [ ] انتخاب stack با ثبت گزینه‌ها، معیارها، ریسک‌ها و تأیید؛ انتخاب فناوری صرفاً بر مبنای پیش‌فرض ابزارها انجام نشود.
- [ ] تهیهٔ ADR برای فناوری‌های کلیدی: frontend/build، backend، پایگاه داده، احراز هویت، SMS، ذخیره‌سازی فایل، میزبانی، صف/worker و پایش.
- [ ] تعریف اهداف اولیهٔ availability، بازیابی، backup/restore، performance، accessibility و پشتیبانی پلتفرم.
- [ ] تعیین فرایند مدیریت اسرار، محیط‌های توسعه/آزمایش/تولید، تغییرات پایگاه داده و rollback.

**شرط عبور:** معماری MVP تصویب شده و هیچ ابهام بحرانی دربارهٔ مرز سرویس‌ها، مالکیت داده یا روش مجاز اتصال وجود نداشته باشد.

## 4. دروازه امنیت، حریم خصوصی و سلامت

- [ ] تکمیل threat model و threat register؛ هر خطر بحرانی یا بالا باید mitigation، مالک و معیار آزمون داشته باشد.
- [ ] تعیین طبقه‌بندی داده و حداقل‌سازی اطلاعات برای هر جریان و سرویس ثالث.
- [ ] تعریف رضایت، مجوز دسترسی، لغو دسترسی، تاریخچهٔ دسترسی و سیاست‌های نگهداری/حذف/خروجی داده.
- [ ] تعیین سیاست دسترسی خانواده، سرپرست و مراقب، از جمله لغو مجوز و سن/وضعیت‌های حساس طبق حوزهٔ قضایی.
- [ ] تعریف ثبت رویداد امنیتی بدون درج OTP، توکن، کلید خصوصی یا محتوای غیرضروری سلامت.
- [ ] تعیین کنترل‌های server-side برای authentication, authorization, ownership, tenant isolation و consent.
- [ ] بررسی مسیر آپلود فایل، نوع و حجم مجاز، اسکن/قرنطینه، دسترسی خصوصی و انقضای لینک‌ها.
- [ ] تعیین نحوهٔ گزارش و رسیدگی به رخداد امنیتی و افشای احتمالی داده.
- [ ] اگر قابلیت بالینی/AI در محدوده است: تعیین مسئول بالینی، فرایند تأیید، حدود کاربرد، نمایش عدم قطعیت، قواعد escalation و پایش پس از انتشار.
- [ ] مستندسازی اینکه SMS OTP و PWA چه محدودیت‌هایی دارند؛ از ادعای ضمانت سخت‌افزاری یا لغو فوری دسترسی آفلاین پرهیز شود.

**شرط عبور:** אין خطر بحرانی حل‌نشده برای محدودهٔ مورد شروع؛ حریم خصوصی و مسئولیت بالینی (در صورت لزوم) دارای مالک و فرایند مشخص باشند.

## 5. دروازه هویت و دستگاه مورد اعتماد

- [ ] ارزیابی و انتخاب provider احراز هویت/SMS یا تصمیم مستدل برای پیاده‌سازی اختصاصی.
- [ ] تعریف registration، تأیید ایمیل، تأیید موبایل، ورود آنلاین و بازیابی حساب به‌عنوان فرایندهای مستقل.
- [ ] تأیید flow ورود موبایلی OTP و رفتار پاسخ‌ها برای جلوگیری از افشای وجود حساب.
- [ ] تعیین انقضا، یک‌بارمصرف‌بودن، محدودیت تلاش/درخواست، resend و رفتار خطای سرویس پیامک.
- [ ] طراحی و آزمون invariant سمت سرور و پایگاه داده: حداکثر یک دستگاه فعال مورد اعتماد برای هر حساب.
- [ ] طراحی جایگزینی دستگاه به‌صورت اتمیک و تعیین رفتار درخواست‌های هم‌زمان.
- [ ] تعریف ابطال نشست‌ها/دستگاه، تغییر شماره موبایل، دستگاه گم‌شده و درخواست مشکوک.
- [ ] تعیین تکلیف داده‌های محلیِ همگام‌نشده هنگام تعویض دستگاه؛ عدم حذف خاموش یا انتقال خودکار کلیدها.
- [ ] مشخص‌کردن تفاوت device identity، session credentials، کلید رمزگذاری داده و مجوز آفلاین.

**شرط عبور:** سناریوهای OTP، brute-force/rate limit، تعویض هم‌زمان دستگاه و ابطال دسترسی، با آزمون قابل تکرار تعریف شده باشند.

## 6. دروازه آفلاین و رمزنگاری

- [ ] تهیهٔ feasibility report برای نسخه‌ها/سیستم‌عامل‌ها و مرورگرهای پشتیبانی‌شده.
- [ ] تعیین اینکه آیا دسترسی آفلاین در MVP لازم است؛ اگر هست، تعیین داده‌های مجاز و کارکردهای محدودشده.
- [ ] مستندسازی اینکه حد ۷۲ ساعت در PWA در برابر تغییر ساعت و دس��گاه کاملاً آفلاین چه تضمین‌هایی دارد و چه محدودیت‌هایی باقی می‌ماند.
- [ ] طراحی چرخهٔ عمر کلید: ایجاد، بازکردن، چرخش، ابطال، بازیابی و رفتار در حذف/خرابی storage.
- [ ] بازبینی مدل رمزگذاری قبل از ذخیرهٔ پایدار؛ کلید اصلیِ بی‌حفاظ کنار دادهٔ رمز‌شده ذخیره نشود.
- [ ] تعیین زمان قفل خودکار، رفتار PIN/biometric، خروج امن و شرایط پاک‌سازی/قفل داده.
- [ ] تعریف سیاست cache برای Service Worker؛ پاسخ‌های سلامت و اسرار احراز هویت به‌طور پیش‌فرض cache نشوند.
- [ ] آزمون رفتار storage eviction، پاک‌شدن دادهٔ مرورگر، restart/termination و بازگشت از حالت آفلاین.
- [ ] تعیین حداقل دادهٔ لازم برای حالت آفلاین و رضایت/تنظیم صریح کاربر.
- [ ] اگر تضمین فنی قابل‌قبول نیست، offline access را برای پلتفرم/دادهٔ مربوط محدود یا از MVP حذف کنید.

**شرط عبور:** سیاست آفلاین، محدودیت‌های پلتفرم، طراحی کلید و بازیابی داده بازبینی شده‌اند؛ هیچ ادعای امنیتی فراتر از آزمون‌ها مطرح نمی‌شود.

## 7. دروازه داده و همگام‌سازی

- [ ] تعریف مدل provenance: دادهٔ تأییدشدهٔ بالینی، گزارش کاربر، واردشده، AI-generated و ثبت آفلاین از هم قابل تشخیص باشند.
- [ ] تعیین server source-of-truth و مشخص‌کردن اینکه هر نوع رکورد در کدام سیستم مالکیت دارد.
- [ ] طراحی شناسهٔ محلی پایدار، idempotency key، versioning و acknowledgement سرور.
- [ ] تعیین رفتار retry، شکست جزئی، upload منقطع، duplicate و رکورد conflict.
- [ ] تعریف UX برای وضعیت محلی، منتظر همگام‌سازی، خطا، همگام‌شده و نیازمند بررسی.
- [ ] اطمینان از اینکه conflict یا اصلاح دادهٔ بالینی هیچ‌گاه بی‌صدا overwrite نمی‌شود.
- [ ] تعیین سیاست attachmentها، اندازه/نوع، ادامهٔ upload و پاک‌سازی محلی.
- [ ] تعریف ثبت audit و معیارهای پایش همگام‌سازی.
- [ ] نوشتن قرارداد API/OpenAPI و آزمون contract قبل از اتصال واقعی.

**شرط عبور:** مسیر موفق و شکست synchronization، duplicate، conflict، revoked device و قطع شبکه مشخص و آزمون‌پذیر باشد.

## 8. آمادگی تیم و مخزن

- [ ] تعیین مسئول هر ماژول و reviewerهای لازم.
- [ ] تعریف conventions کدنویسی، branch/PR، code review و مدیریت dependency.
- [ ] راه‌اندازی CI برای lint، type-check، unit، integration و build.
- [ ] تعریف secret scanning، dependency scanning و قواعد عدم نشر secrets/دادهٔ واقعی.
- [ ] ایجاد محیط‌های development/staging; دادهٔ واقعی بیمار در test/dev استفاده نشود.
- [ ] تعریف seed/sample data مصنوعی و sanitized.
- [ ] تنظیم logging, monitoring, error tracking و health checks بدون دادهٔ حساس.
- [ ] تعریف backup/restore و تمرین بازیابی برای داده‌های حیاتی.
- [ ] ایجاد قالب ADR، issue، PR و test plan.
- [ ] تعریف روش انتشار تدریجی، feature flags و rollback.

## 9. ترتیب پیشنهادی اجرای MVP

ترتیب دقیق باید پس از تعیین محدوده تصویب شود. الگوی پیشنهادی:

1. اسکلت پروژه، CI، design tokens، localization و navigation.
2. API/backend foundation، error handling، logging امن و پایگاه دادهٔ حداقلی.
3. هویت و حساب فقط پس از تصویب provider، threat model و آزمون‌های امنیتی پایه.
4. پروفایل و یک گردش‌کار محدود سلامت با provenance و مجوزهای سمت سرور.
5. اتصال API و audit برای جریان‌های لازم.
6. قابلیت آفلاین محدود فقط پس از عبور از دروازهٔ آفلاین؛ در غیر این صورت online-only در MVP.
7. دسترسی خانواده، AI، telemedicine، community، subscription و package engine در فازهای جداگانه، پس از پذیرش ریسک و نیازمندی مستقل.

## 10. معیار Definition of Done

یک قابلیت فقط زمانی Done است که:

- [ ] معیار پذیرش محصول پاس شده باشد.
- [ ] مجوزهای server-side و مالکیت داده آزموده شده باشند.
- [ ] تست‌های unit/integration/e2e متناسب پاس شده باشند.
- [ ] رفتار خطا، شبکهٔ قطع‌شده و retry تعیین شده باشد.
- [ ] دادهٔ حساس در log، analytics یا cache ناخواسته ظاهر نشود.
- [ ] accessibility، localization و RTL/LTR بررسی شده باشد، اگر برای آن قابلیت کاربرد دارد.
- [ ] مستندات API/UX/تصمیم مرتبط به‌روز باشند.
- [ ] code review و security review لازم کامل شده باشد.
- [ ] محدودیت‌های شناخته‌شده ثبت شده باشند.
- [ ] rollback یا خاموش‌کردن قابلیت تعریف شده باشد.

## 11. چک‌لیست بازبینی پیش از انتشار

- [ ] هیچ secret یا دادهٔ واقعی سلامت در مخزن، log یا ابزار تحلیلی افشا نشده است.
- [ ] دسترسی به رکوردهای کاربر دیگر و آزمون‌های IDOR/tenant isolation بررسی شده است.
- [ ] دسترسی خانواده/مراقب فقط بر اساس مجوز صریح و قابل‌لغو است.
- [ ] پاسخ‌های API دادهٔ بیش از نیاز برنمی‌گردانند.
- [ ] آپلود و دانلود فایل خصوصی و مجازسازی‌شده است.
- [ ] پیام‌های اعلان اطلاعات حساس را ناخواسته افشا نمی‌کنند.
- [ ] backup/restore، incident contact و rollback آماده‌اند.
- [ ] قابلیت‌های بالینی و AI دارای بازبینی و متن محدودیت/ارجاع لازم هستند.
- [ ] ماتریس پلتفرم‌های پشتیبانی‌شده مطابق آزمون واقعی است.
- [ ] همهٔ دروازه‌های لازم امضا شده و خطرهای باقیمانده پذیرفته شده‌اند.
