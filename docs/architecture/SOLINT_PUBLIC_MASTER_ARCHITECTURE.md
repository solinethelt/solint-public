# معماری کلان اپ عمومی سولینت

## ۱. هدف

`solint-public` اپلیکیشن عمومی سولینت است که در نسخهٔ نخست مستقل اجرا می‌شود و در آینده از طریق API به مرکز اصلی سولینت متصل خواهد شد. هدف معماری، فراهم‌کردن این اتصال بدون بازنویسی هستهٔ اپ است.

## ۲. اصول معماری

- استقلال اجرایی از مرکز اصلی در نسخهٔ اولیه
- جداسازی منطق کسب‌وکار از زیرساخت و سرویس‌های خارجی
- ارتباط با مرکز سولینت فقط از طریق یک adapter/client مشخص
- طراحی قراردادهای API و داده به‌صورت نسخه‌پذیر
- ثبت وضعیت همگام‌سازی، خطاها و عملیات حساس
- قابلیت جایگزینی اجزای زیرساخت بدون تغییر منطق دامنه

## ۳. نمای کلی

```text
کاربر (وب/موبایل)
       │
       ▼
رابط کاربری ── API اپلیکیشن ── منطق کسب‌وکار
                                  │
                                  ├── پایگاه دادهٔ محلی
                                  ├── صف کارها / worker
                                  └── لایهٔ اتصال Solint Core
                                               │
                                               ▼
                                      مرکز اصلی سولینت
```

مرکز اصلی یک سرویس خارجی است؛ اجزای دامنه نباید مستقیماً به API یا مدل‌های داخلی آن وابسته شوند.

## ۴. لایه‌ها

### رابط کاربری

وب، پنل مدیریت و در صورت نیاز اپ موبایل. این لایه نمایش داده و تعامل با API را انجام می‌دهد و نباید منطق اصلی کسب‌وکار را پیاده کند.

### API و کاربرد

مسئول endpointها، احراز هویت، اعتبارسنجی ورودی، کنترل دسترسی، محدودسازی نرخ و هماهنگ‌کردن سرویس‌های کاربردی است.

### دامنه

قوانین و مدل‌های اصلی اپ، مانند کاربران، سازمان‌ها، فضاهای کاری، نقش‌ها و مجوزها را نگه می‌دارد. این لایه به دیتابیس، شبکه یا سرویس مرکزی وابسته نیست.

### زیرساخت

پیاده‌سازی ذخیره‌سازی، صف، cache، فایل‌ها، ایمیل، logging و monitoring. این اجزا از طریق interfaceهای تعریف‌شده به لایه‌های بالاتر ارائه می‌شوند.

### اتصال به مرکز سولینت

ماژولی مستقل برای احراز هویت/توکن، فراخوانی API مرکزی، تبدیل مدل‌ها، همگام‌سازی، retry و ثبت خطاها. در نسخهٔ اولیه می‌تواند غیرفعال یا با یک mock جایگزین باشد.

## ۵. داده و همگام‌سازی

داده‌های نسخهٔ اولیه در پایگاه دادهٔ خود اپ نگهداری می‌شوند. مدل‌های پیشنهادی شامل `users`، `organizations`، `workspaces`، `permissions`، `external_connections`، `sync_state` و `audit_logs` هستند.

برای رکوردهایی که با مرکز همگام می‌شوند، وضعیت اتصال باید دست‌کم شامل این موارد باشد:

```text
entity_type, entity_id, remote_id, sync_status,
last_synced_at, last_error, version, updated_at
```

همگام‌سازی باید قابل تکرار و idempotent باشد تا اجرای دوبارهٔ یک درخواست باعث ایجاد رکورد تکراری نشود. برای عملیات قابل‌اعتماد، الگوی outbox مناسب است: تغییر محلی و رویداد همگام‌سازی در یک تراکنش ثبت می‌شوند و worker رویداد را ارسال می‌کند.

## ۶. احراز هویت و دسترسی

در فاز نخست، احراز هویت مستقل اپ استفاده می‌شود. در فاز اتصال، یک adapter امکان اتصال به SSO/OAuth مرکز سولینت را فراهم می‌کند، بدون اینکه منطق دامنه مستقیماً به provider وابسته شود. نقش‌ها و مجوزها باید در سمت سرور بررسی شوند.

## ۷. امنیت و عملیات

- استفاده از HTTPS و نگهداری امن secrets
- حداقل سطح دسترسی برای سرویس‌ها و توکن‌ها
- اعتبارسنجی ورودی و rate limiting
- ثبت audit برای عملیات حساس
- عدم ثبت رمز، توکن یا دادهٔ حساس در log
- health check، metrics، tracing و هشدار برای خطاهای اتصال
- retry با backoff محدود و امکان مشاهده و بازیابی کارهای ناموفق

## ۸. ساختار پیشنهادی پروژه

```text
solint-public/
├── apps/
│   ├── web/
│   └── admin/
├── services/
│   ├── api/
│   └── worker/
├── packages/
│   ├── domain/
│   ├── shared-types/
│   └── solint-client/
├── infra/
└── docs/
    └── architecture/
```

جزئیات ابزارها و چارچوب‌ها پس از تعیین نیازمندی‌ها و محیط استقرار انتخاب می‌شوند؛ پیشنهاد اولیه برای پایگاه داده PostgreSQL و برای کارهای پس‌زمینه یک صف/worker است.

## ۹. مراحل توسعه

1. **نسخهٔ مستقل:** رابط کاربری، API، پایگاه داده و احراز هویت پایه.
2. **آماده‌سازی اتصال:** تعریف interfaceهای مرکزی، مدل شناسهٔ خارجی و mock برای توسعه و تست.
3. **اتصال آزمایشی:** پیاده‌سازی client، مدیریت توکن، ثبت وضعیت sync و retry.
4. **همگام‌سازی تولیدی:** outbox/worker، مانیتورینگ، سیاست حل تعارض و بازیابی خطا.

## ۱۰. تصمیم‌های باز

پیش از پیاده‌سازی باید دامنهٔ کاربرد اپ، پلتفرم هدف (وب/موبایل)، روش احراز هویت، مالکیت داده‌ها، قرارداد API مرکز اصلی، سیاست تعارض داده و محیط استقرار تعیین شوند.

## جمع‌بندی

اپ عمومی سولینت باید اکنون مستقل و قابل‌استقرار باشد، اما از مرزهای فنی مشخص برای اتصال آینده برخوردار شود. لایهٔ اتصال، مدل‌های مرکزی و همگام‌سازی را از هستهٔ دامنه جدا می‌کند تا اتصال بعدی کم‌ریسک و قابل‌آزمون باشد.
